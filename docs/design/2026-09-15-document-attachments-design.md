# Document attachments for PR, PO, RR, AP and CV — design

Date: 2026-09-15. Owner request, verbatim:

> Should all have feature to upload unlimited files and images.
> PR – the signed PR. PO – the signed PO, quotation from vendor(s), other documents.
> RR – the signed RR, DR/SR or any documents from vendor. AP – the signed AP, any other
> documents not included in the previous documents. CV – the signed CV, check and any
> other documents not included in the previous documents.
> Staff can upload as long as the document has not been Approved. Any additional upload
> can be handled in the amendment.
> Reason: Admin and other users find it hard to know whether a record is valid or not
> just based on the Approval status.

## What exists today

- **AP** already has attachments: `AccountsPayableAttachment` (table
  `accounts_payable_attachments`), files under `instance/uploads/accounts_payable/<ap_id>/`,
  routes `upload / download / preview / delete` in `app/accounts_payable/views.py`, a
  create-form queue (files held in the browser until Save) and an edit-mode panel. Upload and
  delete are gated on `status == 'draft'`. Sales Invoice has the same shape.
- **PR, PO, RR, CV** have no attachments at all.
- **Amendment** exists for PR and PO only (`Amendable` mixin, `DocumentRevision`, `/amend`
  route, approve-level gate). RR, AP and CV have no amendment path.

## Decision

### One shared attachment subsystem, not four more copies

A new package `app/attachments/` holds one model, one blueprint, one service module, one
template partial and one static script, and the four modules plug into it through a small
registry. AP keeps its existing table and routes untouched: it already meets the rule, and
moving its rows and files is a migration with no user-visible benefit.

Alternatives considered:

1. Copy the AP pattern into each module (model + helpers + 4 routes + 2 template blocks +
   inline JS, ×4). Fastest to write, but it is exactly the "~3,600 lines of duplicated JS"
   gap CLAUDE.md already flags, and every future rule change (allowed types, gate wording)
   has to be made five times.
2. A per-module table generated by a factory. Keeps FK cascades, but the mapper-registry
   branch guard would then see four new models with no `branch_id`, and the gain over a
   polymorphic table is nil because these documents are never hard-deleted.
3. **Chosen:** one polymorphic table keyed by `(document_type, document_id)`, mirroring
   `DocumentRevision`, which already solved the same problem for the same documents.

### Data model

Table `document_attachments` (`app/attachments/models.py`, class `DocumentAttachment`):

| column | type | notes |
|---|---|---|
| id | Integer PK | |
| document_type | String(40) NOT NULL | `purchase_requests`, `purchase_orders`, `receiving_reports`, `cash_disbursements`. Matches the audit module name, as DocumentRevision does. |
| document_id | Integer NOT NULL | Plain integer, no FK: points at four tables. |
| original_filename | String(255) NOT NULL | `secure_filename()` of what the user chose. |
| stored_filename | String(255) NOT NULL UNIQUE | `uuid4().hex + ext`. |
| mime_type | String(100) NOT NULL | From the server-side extension allowlist, never the client. |
| file_size | Integer NOT NULL | bytes |
| uploaded_by_id | Integer NOT NULL, FK users.id (named `fk_document_attachments_uploaded_by`) | |
| uploaded_at | DateTime NOT NULL, default `ph_now` | |

Index `ix_document_attachments_doc (document_type, document_id)`.

No `branch_id`: an attachment is evidence belonging to its parent document and takes the
parent's branch. Same reasoning as `AccountsPayableAttachment` and `SalesInvoiceAttachment`,
which also carry none.

Files live at `instance/uploads/<document_type>/<document_id>/<stored_filename>`, next to the
existing `accounts_payable/` and `company/` folders.

Allowed types are the AP allowlist verbatim (png, jpg, jpeg, gif, webp, pdf, doc, docx, xls,
xlsx, csv, txt; SVG deliberately excluded because it executes script when served inline).
There is no count limit. The per-request size limit stays `MAX_CONTENT_LENGTH` (16 MB by
default), which on the create form is the total of all queued files.

### Registry: what each document type tells the shared code

`app/attachments/registry.py` maps a `document_type` to an `AttachmentTarget`:

- `load(document_id)` — returns the document or `None` (lazy import of the module's model, so
  the attachments package never imports a views module).
- `number(doc)` — the human document number for audit rows and flash messages.
- `view_endpoint` — where to redirect after an action (`purchase_requests.view`, ...).
- `open_statuses` — statuses in which an edit-level user may upload and delete.
- `edit_roles` — who is edit-level for that document.
- `amend_statuses` and `is_amend_level(user)` — optional; when present, an approve-level user
  may also upload/delete while the document is in an amendable status. That is the "handled in
  the amendment" path.

Values per document:

| type | open_statuses | edit_roles | amend_statuses | amend-level |
|---|---|---|---|---|
| purchase_requests | draft, submitted, rejected | staff, accountant, admin, chief_accountant | `PurchaseRequest.AMEND_STATUSES` | same predicate as `_approve_gate` |
| purchase_orders | draft, submitted | same | `PurchaseOrder.AMEND_STATUSES` | same predicate as `_has_approve_level_role` |
| receiving_reports | draft, submitted | `RR_EDIT_ROLES` | none | n/a |
| cash_disbursements | draft | staff, accountant, admin, chief_accountant | none | n/a |

"Approved" therefore means: PR/PO `approved` and every status after it; RR `approved`
and `billed`; CV `posted`. AP is unchanged: `draft` only, which is the same rule since an AP
is approved by posting it.

`can_upload(target, doc, user)` is the single predicate:

```
(user.role in edit_roles and doc.status in open_statuses)
or (amend_statuses and doc.status in amend_statuses and is_amend_level(user))
```

`can_delete(target, doc, user, attachment)` is `can_upload(...)` and additionally
`attachment.uploaded_by_id == user.id or user.has_full_access or user.role == 'accountant'`,
so staff can undo their own mistaken upload but cannot remove a colleague's evidence.

Download and image preview are open to any logged-in user, as they are for AP.

### Routes (`app/attachments/views.py`, blueprint `attachments`)

| method | path | gate |
|---|---|---|
| POST | `/attachments/<document_type>/<int:document_id>/upload` | login + `can_upload`; field `attachment` (single, edit/amend/detail panel) or `attachments` (multiple, tolerated for the same route). Bad files are skipped with a warning, never a 500. Redirects to `?next=` if it is a safe relative path, else the document's view page. |
| GET | `/attachments/<int:id>/download` | login. `send_file(as_attachment=True)` with the stored MIME type and `X-Content-Type-Options: nosniff`. |
| GET | `/attachments/<int:id>/preview` | login; 404 unless `is_image`. Inline, with `Content-Security-Policy: default-src 'none'; sandbox` exactly as AP does. |
| POST | `/attachments/<int:id>/delete` | login + `can_delete`. Deletes the row, then the file; a missing file is logged, not fatal. |

Unknown `document_type` → 404. A document whose branch is not the selected branch is handled
the same way the module's own view handles it: the registry `load` uses the module's plain
`db.session.get`, and the redirect target is the module's view, which already applies its own
branch rule.

### Service (`app/attachments/service.py`)

- `save_attachment(target, doc, file_storage, user) -> (ok, error_message)` — validates the
  name and extension, writes the file, inserts the row, commits, writes the audit row
  (`log_create`, module `<document_type>_attachment`, identifier `"<number> / <filename>"`).
  On any failure it rolls back and removes the written file. One commit per file, as AP does.
- `save_queued_attachments(target, doc, files, user) -> skipped_names` — the create-form
  helper: loops `request.files.getlist('attachments')`, skips empties, collects the names
  that failed so the caller can flash one warning.
- `delete_attachment(target, doc, attachment, user)` — row first, then file, then
  `log_delete`.
- `attachments_for(document_type, document_id)` — ordered by `uploaded_at`, for templates.
- `file_path(attachment)` — the one place that knows the on-disk layout.

### UI

One partial, `app/attachments/templates/attachments/_panel.html`, rendered with
`document_type`, `document`, `attachments`, `can_upload`, `can_delete_fn`, and an optional
`next_url`. It is the AP panel generalised: heading with file count, an upload form when
`can_upload` is true, the table (filename, type badge, size, uploaded by, date, actions), the
per-image preview modal and the per-row delete modal. When `can_upload` is false the form is
replaced by one line saying uploads are closed and, for PR/PO, that further files are added
through Amend.

Placement:

- **Detail page** of each of the four documents: the panel, after the line-item card. This is
  where an admin looks to judge whether a record is valid, so the signed scan must be here.
- **Edit form** (draft/submitted): the panel, so a staff member editing a draft can attach in
  the same sitting.
- **Amend form** (PR, PO): the panel, gated by the amend-level predicate.
- **Create form**: a "queue" file input (`name="attachments" multiple`) plus the shared script
  `app/static/js/attachment_queue.js`, which lists the chosen files, flags unsupported types
  and lets the user remove one before Save. On a successful create the route saves the queued
  files after the document commit; on a failed create the form re-renders and warns that the
  files must be re-chosen (the browser cannot repopulate a file input).

The four create routes each gain a call to `save_queued_attachments` immediately after their
existing commit and before their success redirect.

### Migration

`migrations/versions/docatt_0001_document_attachments.py`, `down_revision = 'f179afe2918a'`
(the current head). `create_table` with the FK named inline and the composite index. New
table only, so no batch wrapper. Verified by upgrading a **copy** of `instance/philgen.db`
before it is run on the real file.

### What stays out of scope

- AP and Sales Invoice keep their own tables. Folding them into `document_attachments` is a
  data migration for later.
- RR, AP and CV have no amendment path, so after approval/posting their attachments are
  frozen. The owner's rule says additional uploads go through amendment, and those three
  modules have none; giving an admin a post-approval upload there is a separate decision.
- No attachment count on list pages. The detail page is where validity is judged; a list
  badge is a cheap follow-up if wanted.
- No virus scanning, no image thumbnails, no per-file size limit below the request limit.

### Tests

`tests/integration/test_document_attachments.py`, marker `attachments` (registered in
`pytest.ini`), parametrised over the four document types with small factories:

- upload in an open status creates the row, the file and the audit row (through the HTTP
  route, per the CRUD-test rule);
- upload is refused in an approved/posted status for an edit-level user, and the panel on the
  detail page shows no upload form (asserted on the form `action` attribute, not a class name);
- PR/PO: an approve-level user can upload while `approved`; a staff user cannot;
- disallowed extension is refused and nothing is written;
- download returns the bytes with `Content-Disposition: attachment`; preview 404s for a PDF;
- delete: uploader may, another staff user may not, accountant may; the file is gone;
- create form with queued files attaches them after the document is created;
- unknown document type → 404.

Plus `tests/unit/test_attachment_gates.py` for `can_upload` / `can_delete` over the status
tables above.

### Acceptance (owner's finish line)

Each of the five documents is exercised in the running philgen instance through the Chrome
MCP: a draft is opened or created, a PNG and a PDF are uploaded and appear in the panel, the
image preview opens, and an approved/posted document of the same type shows no upload form.
