# Stock Movement Effective Date — Design

**Fixes:** `BUG-STOCKMOVEMENT-CREATEDAT-IGNORES-DOCUMENT-DATE` (HIGH, open since 2026-07-23)
**Work order:** `docs/bug-reports/2026-07-23-stock-movement-created-at-ignores-document-date.md`
**Date:** 2026-08-15

## The defect

`StockMovement` has no business-effective date. It carries only `created_at`
(`default=ph_now`, `app/stock_adjustments/models.py:29`) — the wall-clock moment someone
clicked Approve. A source document's own date (`adjustment_date`, `receipt_date`,
`delivery_date`, `memo_date`) is never copied onto the movement it produces.

Both costing paths order by that posting timestamp:

| Site | Today |
|---|---|
| `app/stock_adjustments/lifo_shadow.py:42` | `.order_by(StockMovement.created_at, StockMovement.id)` |
| `app/stock_adjustments/service.py:138` | `fifo_apply_receive(..., received_at=mv.created_at)` |
| `app/stock_adjustments/fifo.py:35` | layers consumed `.order_by(StockCostLayer.received_at, ...)` |

So **backdating a document has zero effect on where its layer lands in the stack.**

Two things make this HIGH rather than a reporting quirk:

1. It reaches FIFO's *real*, GL-posting costing — so it can produce wrong COGS on the
   actual books, feeding the Income Statement and BIR-facing figures.
2. It is latent. It only bites when documents are posted out of chronological order
   relative to their stated dates — i.e. catch-up and onboarding data entry, which is
   precisely this project's own historical-build pattern
   (`clients/cas/ui-tests/build_january_2026.py` and siblings). In the original repro the
   math came out correct purely because the three adjustments happened to be posted in
   date order in real time.

**A correction to the work order's suggested fix.** It proposes ordering
`fifo_plan_receive`/`fifo_plan_consume` by `(movement_date, created_at, id)`. That does not
work as written: `fifo_plan_consume` never reads `StockMovement`. It reads
`StockCostLayer`, ordering by `received_at` — a column *derived* from `mv.created_at` at
write time. A fix touching only `StockMovement` would leave the GL-posting path, the part
that actually matters, still wrong.

## Why now

Verified 2026-08-15 across every local DB and every client backup: **zero `stock_movements`
rows and zero `stock_cost_layers` rows everywhere.** R-03 costing has never run in
production. The same change once a client is live becomes a real data migration with
posted COGS at stake. The backfill below is still written correctly — dev and demo DBs do
accumulate rows — but the risk today is near zero.

## Decisions

| Question | Decision |
|---|---|
| Editing a document's date after posting | **Snapshot at post time.** The movement keeps the date it was posted with; later edits do not silently re-order the stack. Matches the ledger's existing immutability. Implies a stored column. |
| FIFO's layer table | **Fix `received_at`'s source.** No new column — populate it from the effective date instead of the posting timestamp. `received_at` already means "when the stock was received"; a posting timestamp was always the wrong value. |
| Backdating before an existing consumption | **Block it** with an actionable message. |
| How the date reaches `post_movement` | **Required explicit parameter.** A forgotten caller fails loudly instead of defaulting to today — which is how this bug survived in the first place. |

## Data model

**`StockMovement.movement_date`** — `db.Date`, `nullable=False`, indexed. Date, not
DateTime: every source document carries a `db.Date`, and a time component would fabricate
precision the user never entered.

**`StockLot.received_at`** (specific identification) — same treatment, found while planning
rather than during design. `specific_id_apply_receive` is handed `mv.created_at` at the same
call site (`service.py:144`). Unlike the FIFO layer this is **not** a costing-order bug —
specific-ID consumption is user-picked by `lot_id` and nothing orders lots by `received_at` —
but it is the same wrong value, displayed as the lot's receipt date. Fixed together, since it
is the identical one-line change on the adjacent line.

**`StockCostLayer.received_at`** — no schema change. We change what is *written*:
`datetime.combine(effective_date, time.min)` rather than `mv.created_at`. The column stays
DateTime so nothing downstream breaks, and the posting timestamp is not lost — it stays
reachable via `source_movement_id → movement.created_at`. Ordering remains
`(received_at, id)`; `id` is autoincrement, so it already breaks same-date ties in
insertion order, which is what `created_at` would have done.

### Migration `stkdate_0001`

Hand-written batch ops (`Migrate()` runs without `render_as_batch`, so autogenerated plain
`ALTER` is not runnable on SQLite):

1. `add_column('movement_date', sa.Date(), nullable=True)`
2. `UPDATE stock_movements SET movement_date = DATE(created_at)`
3. `alter_column('movement_date', nullable=False)` + `create_index`
4. `UPDATE stock_cost_layers SET received_at = DATE(received_at)` — normalise existing
   layers to midnight so old and new rows sort consistently

`down_revision` is `pralloc_0001` (head as of 2026-08-15). Re-check before writing the file
— another branch may have advanced it — and verify a single head after, since two branches
forking the same prior head produce a collision that a conflict-free textual merge will not
surface.

## Where each posting path gets its date

`post_movement` gains a required `movement_date`. All ten call sites:

| Posting path | `movement_date` |
|---|---|
| `receiving_reports/stock_posting.py:72` (approve) | `rr.receipt_date` |
| `delivery_receipts/stock_posting.py:58` (approve) | `dr.delivery_date` |
| `stock_adjustments/service.py:419` (approve) | `adjustment.adjustment_date` |
| `sales_memos/je.py:157` | `memo.memo_date` |
| `purchase_memos/je.py:180` | `memo.memo_date` |
| `bill_of_materials/service.py:97` and `:138` | `ph_now().date()` |
| `production_runs/service.py:223` | `ph_now().date()` |
| `work_orders/service.py:183` | `ph_now().date()` |
| `stock_adjustments/service.py:186` (`reverse_document_movements`) | `ph_now().date()` |

The last five mirror what those paths already give their **journal entries**. ProductionRun
has no date column at all. Voids are deliberately dated today across the codebase, because
a reversal is a new event rather than a retro-edit — dating a void back to the original
would let it silently rewrite a closed period.

### The invariant

A movement's date must equal the `entry_date` of the journal entry created by the same
posting. This is enforced by **test, per path**, not structurally — passing the JE into
`post_movement` would couple stock posting to GL posting for no gain.

That test doubles as a probe of the memo paths, whose JE dating was not verified during
design. If a memo dates its JE from something other than `memo_date`, the test fails on day
one and we have found a sibling GL-dating bug — to be **logged, not fixed here**, since
changing a JE's date changes the books.

## The retroactive-insert guard

Lives inside `post_movement`, the single choke point all ten callers pass through.

**Rule.** For a layer-based product (FIFO or LIFO), refuse a **receipt** whose
`movement_date` is *strictly earlier* than `MAX(movement_date)` over all consumption
movements already posted for that product and branch.

Both sides of that comparison are `movement_date` — the business date. Comparing against
the latest consumption's `created_at` would reintroduce the very defect being fixed, since
it would make the guard depend on posting order again.

Strictly earlier, not "on or before": within one date, ordering falls to `id`, so a
same-day receipt lands *after* an issue already posted that day and cannot retroactively
change what that issue consumed. Blocking same-day would break ordinary catch-up entry for
no correctness gain.

**Never blocked:** issues (they consume what exists); voids (dated today, so on or after
everything); non-layered products.

**Error surface.** A domain exception raised from the service and rendered as a flash at
the view layer, following the existing `FifoLayerConsumedError` precedent. The message names
the product, the blocking date, and the two real remedies — date the receipt later, or
reverse the intervening issues.

**Scoped out, deliberately.** Moving-average products share the order-sensitivity in
principle, since the running average is computed sequentially. They are left alone because
`balance_avg_cost_after` is a stored snapshot of the average *as known when that issue
posted* — a defensible historical figure — whereas a FIFO layer is a claim about *which
specific stock* was consumed, and that claim becomes false. Revisit only with an explicit
decision.

## Testing

**The core test must fail on today's code.** Post receipt A dated 1 Feb *first* in real
time, then receipt B dated 1 Jan, then an issue. FIFO must consume B. Today's code consumes
A. The LIFO shadow gets the mirror-image test.

Posting deliberately out of order is the point: the original bug report's own repro came out
correct because its documents happened to be posted in date order, so a chronological test
proves nothing.

**Control on the path not meant to change.** A strictly chronological sequence must produce
byte-identical layer order and COGS to current behaviour. Without it, "we changed ordering"
and "we broke ordering" are indistinguishable.

**Guard tests, each with its control:** backdated-before-last-consumption raises; same-day
receipt succeeds; an issue is never blocked; a moving-average product is never blocked; a
void is never blocked. The four controls are what stop the guard becoming a blanket freeze.

**Mutation proofs**, run and recorded:

| Mutation | Must fail |
|---|---|
| Drop `movement_date` from the FIFO ordering key | the core out-of-order test |
| Loosen the guard's `<` to `<=` | the same-day control |
| Remove the guard entirely | the backdating test |

A surviving mutation means the test is not attacking the guard and gets rewritten.

**Migration verified on a real-DB copy**, not a `create_all()` fixture: upgrade,
`flask integrity-check`, then a downgrade/re-upgrade round trip.

**Expected side effect, not a defect:** making `movement_date` required breaks every
existing test that calls `post_movement`. That is how we prove all ten call sites were found
rather than trusting a grep.

## Out of scope

- **WorkOrder JE dating.** `WorkOrder` carries `actual_end_date` but dates its JE
  `ph_now().date()`. That may be wrong, but it is a *GL* dating question affecting the
  Income Statement, not stock ordering. Separate bug, separate sign-off.
- **Moving-average ordering** — see above.
- **Recomputing historical COGS.** The guard prevents the situation arising; it does not
  repair one. There is no such data today (zero rows everywhere).
